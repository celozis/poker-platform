# ADR-0010: Telegram-бот — отдельный сервис на коде backend, состояние разговора в базе

## Status

Accepted

## Context

Тикет #10 — первая версия бота: согласие на обработку персональных данных, привязка Telegram к игроку по телефону, выбор клуба и расписание его турниров. Бот должен подниматься через `docker compose` и работать локально, без публичного адреса (webhook появится при деплое, #14). Обработчики должны быть покрыты тестами без настоящего Telegram.

ADR-0001 выбрал aiogram 3, который «делит доменный код с backend». ADR-0002 — синхронные сессии SQLAlchemy. ADR-0007 — уведомления табло живут в памяти одного процесса backend.

## Decision

1. **Отдельный сервис `bot` в docker compose из того же образа и кода, что backend** (`backend/app/bot/`, запуск `python -m app.bot`). Бот работает с базой напрямую, через модели и общий код (`normalize_phone`, окно отметки прихода). Он стартует, когда backend здоров (healthcheck по `/api/health`), то есть миграции уже применены. Бот сам миграции не запускает: два процесса, одновременно применяющие миграции, могли бы помешать друг другу.
2. **Long polling в прототипе.** Публичный адрес не нужен. На одного бота (токен) — один процесс polling.
3. **Состояние разговора хранится в таблице `telegram_users`**, а не в памяти (не FSM aiogram): `telegram_id` (он же id личного чата), время согласия, `player_id` (уникальный), `club_id`. На любое сообщение бот отвечает с первого несделанного шага: согласие → телефон → клуб → готово. Перезапуск бота ничего не теряет, повторный `/start` не создаёт дублей.
4. **Два модуля.** `app/bot/conversation.py` — шаги разговора: синхронные, получают сессию и залоченную строку `telegram_users`, возвращают ответы (текст и кнопки). `app/bot/telegram.py` — обработчики aiogram: достают из сообщения нужное, запускают шаг в отдельном потоке (`asyncio.to_thread`, своя сессия на шаг, коммит после шага), чтобы база не держала остальные чаты, и отправляют ответы. Данные кнопок — `CallbackData` aiogram (`ConsentAnswer`, `ClubChoice`).
5. **Привязка.** Засчитывается только собственный контакт пользователя (`contact.user_id` = отправитель): такой номер Telegram подтвердил. Известный лиге телефон привязывается к существующему игроку, имя не меняется (ADR-0005). Новый телефон заводит игрока с именем из Telegram и временем согласия, данного в боте. Если телефон подтвердил другой Telegram-аккаунт (номер переехал), привязка переходит к нему. Принимаются только российские номера `+7`, как и в админке.
6. **Выбор клуба добавляет игрока в список игроков клуба** (`club_players`, решение заказчика). Администратор клуба сразу видит игрока и может записать его на турнир. Запись из бота (#11) всё равно этого потребует. Если игрок с уже выбранным клубом привязывается заново к другому игроку (сменился номер), тот тоже попадает в список клуба. Доступ бота к данным клуба в обход `AdminClub` и решение не вводить пока RLS описаны в ADR-0003.
7. **Расписание** — несостоявшиеся турниры клуба (`scheduled`), не больше 10 ближайших: дата, время по лиге (UTC+7, как у сезонов), бай-ин. Десять покрывают пару недель, а сообщение гарантированно укладывается в лимит Telegram (4096 символов). Турнир, который не начали и не отменили, пропадает из расписания, когда закрывается отметка прихода (через 12 часов после начала): игрок на него уже не придёт.
8. **Только личные чаты.** В группе бот молчит.
9. **Тесты — через настоящий диспетчер aiogram.** `tests/bot.py` подменяет Telegram на уровне сессии бота (`BaseSession`): апдейты подаются в диспетчер, запросы бота записываются. База — настоящая тестовая PostgreSQL. Последствия работы бота проверяются через админ-API (список игроков клуба, добавление игрока по телефону, турниры), без запросов в базу.

## Consequences

- Плюс: вся логика и данные в одном месте, общий код без копирования, один образ.
- Плюс: тесты проходят весь путь от апдейта Telegram до базы и не зависят от внутреннего устройства бота.
- Минус: **бот и backend — разные процессы.** Уведомления в реальном времени (ADR-0007) живут в памяти backend, поэтому изменение, сделанное ботом, само до админ-панели и табло не дойдёт. Для записи из бота (#11, «появляется в админ-панели без перезагрузки») нужен общий канал: PostgreSQL `LISTEN/NOTIFY` в `app/realtime.py` (он же нужен для нескольких процессов backend) или вызов backend из бота.
- Минус: бот не перезагружается сам при правке кода (backend — да): `docker compose restart bot`.
- Минус: при деплое polling заменится на webhook; `create_dispatcher` от этого не меняется, меняется только `app/bot/__main__.py`.
- Минус: отзыв согласия (152-ФЗ) и удаление данных по запросу игрока пока не сделаны.
