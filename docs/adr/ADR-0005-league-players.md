# ADR-0005: Игрок один на всю лигу, у клуба — свой список игроков

## Status

Accepted

## Context

Один человек может играть в разных клубах лиги, а рейтинг лиги сквозной (клуб → город → Россия/СНГ). Поэтому игрок не может принадлежать одному клубу, как турнир. При этом у клуба свой круг гостей, и администратор работает только с ним. Персональные данные игроков (имя, телефон) подпадают под 152-ФЗ: их обработка требует согласия, и лишние люди не должны их видеть.

Тикет #5 требует: повторный ввод уже известного лиге телефона не создаёт дубль, а подтягивает существующего игрока в клуб; поиск по имени или телефону.

## Decision

- **Таблица `players` без `club_id`**: общие данные лиги, как и предусматривал ADR-0003. Телефон уникален и хранится в виде `+7XXXXXXXXXX` (та же нормализация, что при входе администратора). Время первого согласия на обработку данных — `consent_given_at`.
- **Таблица `club_players` (`club_id`, `player_id`)** — список игроков клуба. Все клубные адреса видят игроков только через неё.
- **Добавление игрока** — `INSERT … ON CONFLICT DO NOTHING` по телефону, затем такое же добавление в `club_players`. Если телефон уже есть в лиге, имя игрока не меняется: его ввёл клуб, который завёл игрока первым. Ответ говорит, что произошло (`created`, `added_to_club`, `already_in_club`), чтобы админ видел, под каким именем игрок уже известен.
- **Согласие обязательно** при каждом добавлении, в том числе когда игрок уже есть в лиге: согласие собирает администратор того клуба, куда пришёл игрок.
- **Поиск идёт только по списку своего клуба** (решение заказчика при реализации тикета #5). Игрока из другого клуба админ подтягивает, вводя его полный телефон в форме нового игрока. Имена чужих игроков через поиск не видны.
- **Регистрации (`registrations`) несут `club_id`** (ADR-0003) и ссылаются на турнир и игрока. Пара (турнир, игрок) уникальна в базе; кроме того, регистрация блокирует строку турнира, так что параллельные запросы не проходят проверки одновременно.

## Consequences

- Плюс: сквозной рейтинг лиги будет считаться по одному `player_id`, без склейки дублей.
- Плюс: доступ к игрокам по-прежнему проверяется в одном месте: соединение с `club_players` по `club.id` из `AdminClub`.
- Минус: админ, знающий чужой телефон, может подтянуть игрока в свой клуб и увидеть его имя. Для MVP это приемлемо: так админ и работает с новым гостем. Если понадобится защита, подтверждение будет через SMS-код игроку.
- Минус: имя, введённое первым клубом с ошибкой, другие клубы исправить не могут. Правка профиля игрока — отдельная задача.
- Минус: `consent_given_at` хранит только первое согласие. Если потребуется доказывать согласие для каждого клуба, время согласия переедет в `club_players`.
