# ADR-0007: Табло в зале — секретная ссылка, WebSocket «турнир изменился» и отсчёт до одного момента

## Status

Accepted

## Context

Тикет #7: табло для телевизора в зале клуба. Это страница без входа, открывается по ссылке турнира. На ней текущий уровень, отсчёт, следующий уровень, число игроков и re-entry, средний стек, ближайший перерыв. Любое действие администратора появляется на табло меньше чем за секунду, через WebSocket, а не опросом. При обрыве связи табло переподключается само. Таймер табло не расходится с таймером админ-панели.

Нужно было решить:

1. **Какая ссылка у табло без входа.** Номер турнира (`/board/42`) или секретный код.
2. **Что и как отправлять по WebSocket.** Готовое состояние табло из обработчика действия администратора или только сигнал «турнир N изменился».
3. **Как связать синхронные обработчики с async WebSocket.** HTTP-обработчики синхронные и работают в пуле потоков (ADR-0002), WebSocket живёт в event loop.
4. **Как не дать таймерам разойтись.** До этого сервер отдавал остаток уровня в целых секундах, округлённых вверх, и каждый экран считал от момента получения.
5. **Как посчитать средний стек.** В турнире не было сказано, сколько фишек даёт add-on.

## Decision

1. **Секретный код.** У турнира есть `board_token`, 12 случайных шестнадцатеричных знаков (`secrets.token_hex(6)`, около 2,8·10¹⁴ вариантов). Ссылка на табло имеет вид `/board/<код>`, API — `GET /api/board/<код>` и `WS /api/board/<код>/ws`. Это единственное исключение из правила «данные клуба видит только его админ» (ADR-0003): по ссылке видно только то, что и так висит на экране в зале. Имён игроков на табло нет. Перебором номеров чужие табло не найти. Так решил владелец проекта при реализации тикета #7.
2. **Сигнал «изменился», состояние читается заново.** После фиксации изменения (`session.commit()`) обработчик вызывает `realtime.tournament_changed(id)`. Каждое подключённое табло этого турнира заново читает своё состояние из базы и отправляет его целиком (`BoardState`, тот же ответ, что у `GET`). Поэтому последнее отправленное состояние всегда не старше последней фиксации, даже если два быстрых действия уведомили в обратном порядке. Несколько изменений подряд сливаются в одно чтение. При подключении табло сначала подписывается, потом отправляет первое состояние, поэтому изменение между ними не теряется. Переподключившееся табло получает состояние на момент подключения. Соединение с неизвестным кодом сервер сначала принимает, а потом закрывает с кодом 4404. Если отказать до `accept`, браузер увидит обычный сетевой сбой (код 1006) и не отличит неверную ссылку от обрыва связи.
3. **Подписчики в памяти процесса.** `app/realtime.py` держит для каждого турнира набор подписчиков (`asyncio.Event` и его event loop). Уведомление из потока пула доходит до подписчика через `loop.call_soon_threadsafe`. Чтение состояния для WebSocket идёт синхронно в пуле потоков (`run_in_threadpool`), каждый раз в своей короткой сессии: сессия, открытая на всё время соединения, держала бы соединение с базой из пула часами. Для async-сессий SQLAlchemy остаётся в силе ADR-0002.
4. **Остаток с точностью до миллисекунды и общий код отсчёта.** `ClockOut.seconds_left` стал дробным (миллисекунды). Админ-панель и табло используют один хук `useCountdown` (`frontend/src/blindClock.ts`). Он считает момент окончания как «момент получения + остаток», показывает целые секунды, округлённые вверх, и обновляется 4 раза в секунду. Два экрана расходятся не больше чем на задержку сети и четверть секунды. Раньше расхождение могло доходить почти до секунды. Когда время уровня вышло, экран снова спрашивает сервер: переход уровня по времени считает только сервер (ADR-0006). Если ответа нет, экран повторяет вопрос каждые 2 секунды, чтобы не застыть на 00:00.
5. **Фишки за add-on — поле турнира.** `addon_stack` обязателен, если add-on разрешён, и не хранится, если нет. Средний стек = (стартовый стек × (игроков + re-entry) + фишки за add-on × число add-on) / игроков в игре. Re-entry даёт стартовый стек. Фишки выбывших остаются в игре. Миграция 0006 заполнила `addon_stack` у старых турниров с add-on стартовым стеком.

## Consequences

- Плюс: задержка табло — это время ответа HTTP-действия плюс одно чтение. Вживую через прокси фронтенда она составила 17–29 мс.
- Плюс: табло не может показать устаревшее состояние после более свежего. Пропущенные при обрыве изменения не нужно досылать.
- Плюс: `realtime.tournament_changed` подходит и для других слушателей (админ-панель на втором устройстве, бот) без изменений в действиях.
- Минус: **подписчики живут в памяти одного процесса.** Если запустить backend в несколько процессов (`uvicorn --workers N`) или на несколько машин, уведомление не дойдёт до табло, подключённого к другому процессу. Тогда нужен общий канал: PostgreSQL `LISTEN/NOTIFY` (достаточно, база уже есть) или брокер. Меняется только `app/realtime.py`.
- Минус: каждое табло читает базу при каждом изменении. При десятках экранов на турнир чтение стоит делать один раз на турнир и рассылать всем. Для 2–3 телевизоров в клубе это не нужно.
- Минус: секретную ссылку, попавшую к постороннему, нельзя отозвать. Для этого понадобится кнопка «сменить код табло».
- Для деплоя (#13): backend запускается одним процессом (об этом комментарий в `backend/Dockerfile`), обратный прокси должен пропускать WebSocket на `/api/board/*/ws` (заголовки `Upgrade`/`Connection`) и отдавать `index.html` на `/board/*`.
