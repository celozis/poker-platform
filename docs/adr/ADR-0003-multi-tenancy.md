# ADR-0003: Мультитенантность — общие таблицы с `club_id` и проверка доступа в API

## Status

Accepted

## Context

В лиге 50 независимых клубов, в MVP их 2–3. Данные клуба (администраторы, турниры, регистрации, касса) принадлежат этому клубу. Администратор одного клуба не должен видеть и менять данные другого. При этом у лиги есть общие данные: игроки и сквозной рейтинг (клуб → город → Россия/СНГ).

Спек #1 предлагает три варианта:

1. **Отдельная схема PostgreSQL на клуб.** Сильная изоляция, но каждую миграцию надо прогонять 50 раз. Общий рейтинг лиги пришлось бы собирать запросами поверх 50 схем, а подключение нового клуба стало бы операцией над схемой БД.
2. **Общие таблицы с колонкой `club_id`, проверка доступа в приложении.** Одна схема и одна миграция. Кросс-клубные отчёты лиги — обычные SQL-запросы. Изоляцию обеспечивает код, поэтому одна забытая проверка открывает чужие данные.
3. **То же плюс Row-Level Security (RLS) в PostgreSQL.** Изоляцию гарантирует сама база. Цена — отдельная роль БД без прав суперпользователя (суперпользователь обходит RLS), `SET app.club_id` в начале каждого запроса и политики на каждой таблице.

## Decision

Выбираем вариант 2, RLS оставляем на будущее (вариант 3) как дополнительную защиту.

- Каждая таблица с данными клуба имеет колонку `club_id` (внешний ключ на `clubs`, с индексом). Общие данные лиги (`clubs`, в будущем игроки и рейтинг) живут в таблицах без `club_id`.
- Все эндпоинты с данными клуба находятся под префиксом `/api/clubs/{club_id}/...` (`app/clubs.py`) и получают клуб только через зависимость `AdminClub`. Она берёт администратора из сессии и отвечает **403**, если `club_id` из URL не совпадает с клубом администратора. Без входа — **401**.
- Запросы к данным клуба фильтруются по `club.id` из `AdminClub`, а не по параметру из URL или тела запроса.
- Администратор принадлежит ровно одному клубу (`admins.club_id`). Если появятся пользователи с доступом к нескольким клубам (владелец сети), проверка в `AdminClub` заменится на проверку членства, а маршруты не изменятся.
- Тест `tests/test_club_access.py` проверяет, что запрос к чужому клубу получает 403. Каждый новый клубный эндпоинт должен получить такой же тест.

## Consequences

- Плюс: одна схема, одна цепочка миграций, отчёты лиги — обычные JOIN.
- Плюс: вся проверка доступа сосредоточена в одной зависимости, её легко найти и протестировать.
- Плюс: подключение нового клуба — это одна строка в `clubs`, без изменений схемы.
- Минус: изоляция держится на дисциплине кода. Эндпоинт, который обходит `AdminClub` или фильтрует по «сырому» `club_id` из запроса, откроет чужие данные. Смягчение: префикс `/api/clubs/{club_id}` плюс обязательный тест на 403 для каждого клубного эндпоинта.
- Пересмотреть и добавить RLS, когда клубных таблиц станет больше нескольких или к БД начнут ходить другие сервисы (бот, отчёты). Модели и API при этом не меняются: добавляются роль БД, политики и `SET app.club_id` в `get_session`.
