# ADR-0001: Технологический стек платформы

## Status

Accepted

## Context

Платформа Сибирской лиги покера должна:

- синхронизировать табло, админ-панель и бота в реальном времени (<1 с) через WebSocket;
- держать данные 50 независимых клубов в одной системе с изоляцией по клубу и общим рейтингом лиги;
- хранить персональные данные игроков на российских серверах (152-ФЗ);
- давать игрокам вход через Telegram-бота как основную точку входа;
- разрабатываться небольшой командой с активным использованием AI-агентов, поэтому стек должен быть распространённым, хорошо типизированным и легко тестируемым.

## Decision

- **Backend: FastAPI (Python 3.12).** Нативные WebSocket и async-обработчики, автоматическая OpenAPI-схема, простое тестирование через `TestClient`. Тот же язык, что у бота, — общий код доменной модели.
- **ORM и миграции: SQLAlchemy 2 + Alembic.** Типизированный декларативный API, миграции схемы применяются автоматически при старте backend (`alembic upgrade head`). Выбор между синхронными и асинхронными сессиями описан в ADR-0002.
- **База данных: PostgreSQL 16.** Надёжная реляционная БД для кассы (атомарные транзакции), поддерживает оба варианта мультитенантности (схема на клуб или RLS по `club_id`), доступна как managed-сервис у российских облаков (Яндекс.Облако).
- **Frontend: React 18 + TypeScript, сборка Vite, тесты Vitest + Testing Library.** Одно SPA-приложение для админ-панели, кабинета игрока, кабинета дилера и табло. Tailwind CSS подключим вместе с первым экраном с реальной вёрсткой.
- **Telegram-бот: aiogram 3.** Async-фреймворк на Python, работает через webhook, делит доменный код с backend.
- **Локальная разработка: Docker Compose.** `docker compose up` поднимает PostgreSQL, backend и frontend на чистой машине.
- **CI: GitHub Actions.** Backend-тесты идут против настоящего PostgreSQL (service-контейнер), без моков ORM; frontend — typecheck и Vitest.

## Consequences

- Плюс: один язык (Python) для API и бота, один (TypeScript) для всех веб-интерфейсов.
- Плюс: весь стек open-source и разворачивается на российском VM без внешних зависимостей.
- Плюс: тесты backend ходят в реальную БД, поэтому ловят ошибки миграций и SQL.
- Минус: Python медленнее Go/Node на CPU-bound задачах; для нашей нагрузки (десятки клубов, сотни одновременных игроков) это не узкое место.
- Минус: тестам backend нужен запущенный PostgreSQL (локально — через `docker compose`).
